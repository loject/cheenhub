# Архитектура соединений

CheenHub использует REST как основной control plane для общих пользовательских
запросов: аккаунт, профиль, авторизация, список серверов, инвайты, загрузка
изображений и другие действия вне конкретной realtime-сессии идут через HTTP API.

Server-scoped realtime работает через отдельное соединение. Основной транспорт -
WebTransport, если он доступен в браузере и не заблокирован сетью. Клиентская
архитектура рассчитана на отдельное realtime-соединение для каждого активного
сервера, а не на одно глобальное соединение. Это нужно для будущих self-hosted
серверов, где у каждого сервера может быть свой base URL и свой realtime endpoint.

Если WebTransport недоступен или не подключается, клиент должен переключаться на
WebSocket fallback. Fallback использует те же realtime envelopes для надежных
запросов и событий. Голосовые/media datagrams передаются WebSocket binary
сообщениями; это медленнее и может добавлять задержку, потому что работает поверх
TCP.

Backend-границы:

- WebTransport принимает `/realtime` на отдельном WebTransport listener.
- WebSocket fallback принимает `/api/realtime/ws` на HTTP API listener.
- Feature-модули получают уже аутентифицированные envelopes и не знают детали
  транспорта.
- Shared realtime hub рассылает надежные события и media bytes без утечки
  WebTransport/WebSocket деталей в продуктовые фичи.

## Завершение процесса

Backend завершает соединения перед выходом процесса:

- `SIGTERM` переводит процесс в фазу завершения: `GET /health` отвечает `503`,
  HTTP-слушатель прекращает приём соединений, а WebTransport-слушатель закрывает
  QUIC endpoint и ждёт отправки закрытия.
- Активные транспорты получают код `1013` (try again later). Клиент восстанавливает
  соединение через существующие ping-watchdog и backoff; отдельного ускоренного
  пути для этого кода пока нет.
- Завершение HTTP не уничтожает realtime-задачи: процесс ждёт слушатель и
  зарегистрированные обработчики до 25 секунд, затем сообщает о таймауте.
- Клиент возвращается в серверную голосовую комнату, если пользователь не отменил
  вход и не выбрал другую цель. Личные звонки восстанавливает модуль звонков.

Голосовое присутствие, набор сообщения и личные звонки хранятся в памяти процесса,
поэтому после старта нового процесса они пусты. Серверное голосовое присутствие
восстанавливается повторным входом клиентов, а не общим состоянием.
